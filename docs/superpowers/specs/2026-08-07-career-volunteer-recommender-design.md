# 求职志愿规划系统设计

**日期：** 2026-08-07  
**状态：** 已批准，自动实施  
**产品名称：** AI 岗位查询与智能简历生成小程序

## 1. 产品定位

产品从“岗位查询工具”升级为“求职志愿规划助手”。

它借鉴高考志愿规划的结果表达方式，但不输出录取概率、不承诺 Offer。它基于用户可验证的资料，给出：

- 冲刺岗位：方向匹配但仍存在关键技能或门槛缺口。
- 稳妥岗位：专业、能力证据与岗位门槛比较匹配。
- 保底岗位：入门门槛较低、可迁移能力较强、适合作为过渡或积累经验的方向。

每一项推荐必须显示评分、理由、证据不足点和下一步行动，避免黑盒排序。

## 2. 交付范围

### 2.1 第一阶段功能

1. 岗位知识库：12 个岗位大类、至少 200 个核心岗位。
2. 专业知识库：常见专业分组、别名和与岗位大类的映射。
3. 求职志愿档案：身份、专业、学历、毕业时间、城市、薪资、行业、工作类型、技能和经历证据。
4. 可解释推荐引擎：按冲刺、稳妥、保底三档输出岗位。
5. 专业与岗位匹配报告：匹配等级、可复用课程/经历、缺失技能、7 天与 30 天行动计划。
6. 移动端规划工作台：填写档案、查看分档、比较岗位、生成简历和返回岗位详情。

### 2.2 保持不变

- 岗位分析、身份咨询、简历批改、简历草案、模板、Word/PDF 导出。
- 现有 CSV 或草稿数据格式。
- 现有可选 Tavily 联网搜索接口和默认禁用策略。
- 不覆盖用户已有的真实简历经历。

### 2.3 不在第一阶段实现

- 未经书面授权的招聘平台爬虫、批量职位同步、反爬绕过。
- Offer 概率、薪资保证、自动投递或代替用户沟通。
- 账号体系、支付体系和企业端后台。

## 3. 数据设计

### 3.1 岗位知识库

新增 SQLite 表 `role_profile`，每一行一个标准岗位：

- `role_name`：标准岗位名，主键。
- `family`：岗位大类。
- `aliases_json`：别名与模糊匹配词。
- `recommended_majors_json`：高度匹配专业。
- `adjacent_majors_json`：可迁移专业。
- `relevant_courses_json`：可复用课程、实验与能力。
- `required_skills_json`：核心技能。
- `entry_skills_json`：初级入门技能。
- `alternative_roles_json`：相近、保底和过渡岗位。
- `internship_roles_json`：适合实习/校招的岗位名称。
- `entry_difficulty`：1 至 5 的入门门槛。
- `industry_tags_json`：行业标签。
- `description`：简短、可用于界面的岗位说明。

使用静态种子数据初始化 12 个大类至少 200 个岗位。种子数据按岗位族谱维护，而不是从招聘平台复制职位文本。

12 个大类：

1. 软件研发
2. 人工智能与算法
3. 数据与数据平台
4. 测试与质量工程
5. 云计算、运维与安全
6. 产品、项目与解决方案
7. 设计与内容创意
8. 市场、品牌与增长
9. 运营、电商与客户成功
10. 销售、商务与供应链
11. 财务、法务、人力与行政
12. 机械、电子、制造、能源与生物医药

### 3.2 专业知识库

新增 SQLite 表 `major_catalog`：

- `major_name`：标准专业名，主键。
- `category`：专业学科分组。
- `aliases_json`：专业别名。
- `related_families_json`：关联岗位大类。
- `transferable_skills_json`：可迁移能力。

支持三种录入方式：

1. 下拉推荐专业。
2. 手动输入未收录专业。
3. “跨专业/专业不限”。

未收录专业不报错；匹配引擎以通用能力和用户技能作为主要证据，并降低专业分项权重。

### 3.3 求职志愿档案

新增 SQLite 表 `career_profile`，以当前 `client_id` 作为主键：

- `client_id`
- `payload_json`
- `created_at`
- `updated_at`

档案字段：

- 身份：复用现有五类身份。
- 专业、学历、毕业时间。
- 目标城市、期望薪资、行业偏好、工作类型。
- 自评技能标签。
- 可选简历草稿 ID，用于提取已有项目、实习、课程与技能证据。

档案仅保存用户输入，不保存外部搜索结果。

## 4. 可解释推荐引擎

### 4.1 总分

总分范围 0 至 100，由可解释分项相加：

| 分项 | 权重 | 依据 |
| --- | ---: | --- |
| 专业匹配 | 30 | 高度关联专业、相近专业、跨专业和未收录专业的处理 |
| 技能匹配 | 25 | 档案技能和简历证据命中核心技能的比例 |
| 入门可行性 | 20 | 身份、学历、毕业时间和岗位入门门槛 |
| 偏好匹配 | 15 | 城市、行业、薪资、工作类型偏好 |
| 市场信号 | 10 | 已启用且可核验的公开来源；无联网来源时中性处理 |

所有分项返回 `score`、`reason` 和 `missing_evidence`。前端展示明细，不只展示总分。

### 4.2 分档规则

先筛除明显不符合用户硬性偏好的岗位，再按总分排序，按以下规则分档：

- 冲刺：总分不低于 60，且至少一项关键技能或门槛存在缺口；优先展示 3 至 5 个。
- 稳妥：总分不低于 70，专业或技能证据较充足，门槛可行；优先展示 3 至 5 个。
- 保底：总分不低于 55，入门可行性较高，技能可迁移，可用于实习、过渡或积累；优先展示 3 至 5 个。

当某一档不足 3 个时，显示原因并推荐用户调整城市、行业或技能偏好，而不是用不相关岗位填充。

### 4.3 专业匹配等级

- 高度匹配：专业在岗位的推荐专业列表中。
- 可迁移：专业在相近专业列表中，或课程/技能命中较多。
- 需要补齐：有可迁移能力，但缺少两项以上核心技能。
- 跨度较大：缺少专业关联和技能证据，仅可展示为冲刺或长期转行方向。

每个推荐岗位同时返回：

- 可复用课程、项目、实验和通用能力。
- 高优先级技能缺口。
- 7 天快速验证任务。
- 30 天项目与投递准备计划。
- 相近岗位与过渡岗位。

## 5. 接口设计

新增后端接口：

```text
GET  /api/role/suggestions?q=
GET  /api/major/suggestions?q=
GET  /api/role/families
POST /api/career/profile/save
GET  /api/career/profile?client_id=
POST /api/career/recommend
```

`POST /api/career/recommend` 接收档案数据或已保存的 `client_id`，返回：

```json
{
  "profile_summary": {},
  "tiers": {
    "stretch": [],
    "stable": [],
    "safe": []
  },
  "major_report": {},
  "action_plan": []
}
```

推荐接口不调用外部搜索。前端仍可对单个岗位主动调用现有 `/api/job/market-search`。

## 6. 前端流程

### 6.1 入口

在岗位搜索页新增“求职志愿规划”入口。页面可继续用于直接查询单个岗位。

### 6.2 志愿规划页

新增独立页面，避免继续堆叠现有岗位搜索页：

1. 基础档案：身份、专业、学历、毕业时间。
2. 偏好：城市、行业、薪资、工作类型。
3. 能力证据：技能标签、关联草稿、项目/实习是否具备。
4. 生成志愿方案。
5. 结果页：冲刺/稳妥/保底标签页、岗位卡、分项得分、缺口、行动计划、制作简历入口。

页面采用当前浅色移动端工作台风格。岗位名、专业名和理由必须换行显示，不允许文本截断。

## 7. 简历联动

从推荐结果进入简历制作时：

- 选择一个目标岗位。
- 保留已有简历数据。
- 在项目经历为空时补两条项目草案。
- 在实习/工作经历为空时补一条实习草案。
- 草案根据专业匹配报告优先描述可复用课程、实验、工具或通用能力。
- 不能生成虚构公司、日期、项目结果或证书。

## 8. 测试与验收

### 后端

- 初始化后 `role_profile` 至少 200 条，覆盖 12 个大类。
- “数据”“工程师”“运营”“设计”等搜索词有多岗位联想。
- 专业联想支持预设、手动和跨专业。
- 相同输入得到稳定排序。
- 高度匹配、可迁移、需要补齐、跨度较大四类均有测试。
- 冲刺/稳妥/保底分档不重叠，且每项都有可解释分项。
- 未配置市场搜索时仍能推荐。

### 前端

- 志愿档案保存、恢复与修改。
- 三档岗位结果和分数明细映射。
- 从岗位卡进入现有简历制作流程。
- 所有长文本在窄屏下可换行。
